Where an on-device answer spends its time

What happens between tapping send and the last word, which knobs Anu has, what today's measurements on LiteRT-LM 0.18.1 showed, and what to try next.

Model: Gemma 4 E4B, generic CPU fileDevice: anu_api36 emulator, 4 coresRuntime: LiteRT-LM 0.18.1

One turn, measured

Each turn goes through up to four steps. Load maps the 3.66 GB model into memory; it happens once per app session (warm start, ADR-074, does it before you type). Create sets up a conversation. Prefill reads every token the model hasn't seen yet. Decode writes the answer one token at a time.

Medians of three runs on 0.18.1, 32-bit activations. Load (6.4–7.7 s with a warm weight cache) is left out because warm start hides it. On the Pixel 10 Pro's CPU the same long prompt takes about 14 s to its first word, because the phone reads at about 57 tokens/s where this emulator reads at about 200.

Two phases, two bottlenecks

Prefill: reading

~200 tok/s

All the new tokens go through the network together as one big matrix multiply. That keeps the arithmetic units busy, so it's compute-bound. More parallel hardware helps a lot: on the Pixel, the GPU read the same prompt 4.6× faster than the CPU (263.6 against 57.4 tok/s).

Decode: writing

~30 tok/s

Each new token needs a pass over essentially all of the weights, yet it does little maths per byte. So it's memory-bandwidth-bound, and the GPU barely helped it on the Pixel (5.5 against 5.8 tok/s). Speculative decoding attacks this phase by guessing several tokens and checking them in one pass. On the Pixel's CPU it gained nothing (ADR-069).

The KV cache is what makes a follow-up cheap. While reading, the model keeps each token's attention keys and values. A later message then only has to read its own new tokens. Anu keeps one LiteRT-LM Conversation alive as that cache (ADR-018), and the saved transcript stays the source of truth. If the cache can't be reused, the whole visible chat is read again: that's the "Catching up on this chat…" line.

When Anu reads the chat again

The cached conversation is reused only when the new request has the same system prompt, tools, sampling and thinking setting as the previous turn, and continues exactly the history it already read (LiteRtLmBrain.kt:301).

  • 0.18.1 matches 0.17.1 on the CPU. The 0.17.1 run was the session's first, with a cold cache and the app holding another copy of the model, which explains its slow load and short answer. Prompt reading, the steady figure, is the same.
  • 16-bit activations bought nothing. The emulator's CPU has 16-bit float instructions (fphp, asimdhp) and int8 matrix instructions (i8mm). Gemma's CPU file stores its weights as small integers, and the heavy maths runs in integer kernels, so the float type between layers barely matters. ADR-096 leaves it unset.
  • The role change is safe. 0.18 sends the model's earlier turns as "assistant". A new contract test rebuilds a chat from the transcript and the model recalls its own suggestion. All 5 contract tests pass, and cancel took 35 ms against a 500 ms target.

What would actually make it faster

  1. The GPU on the Pixel. The biggest measured lever: 14.3 s to 3.3 s for the first word of a long prompt. It needs the clean idle-phone run of the contract and extraction tests that ADR-059 asks for, and your go to install on the phone.
